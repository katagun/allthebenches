# Route prices and measured performance

OpenRouter endpoint observations remain separate from model benchmark scores. A serving route identifies an already reviewed provider endpoint; imported rows join only when its exact upstream model ID, provider name, tag, and service tier reproduce the existing route ID. The importer does not create or match routes from model names.

`RoutePerformance` stores one reported percentile per route, metric, optional workload, source window, and capture time. The endpoint response provides p50, p75, p90, and p99 values over the preceding 30 minutes. The importer maps each `latency_last_30m.{p50,p75,p90,p99}` value to a latency percentile and preserves its original number in `source_value`. The endpoint API does not document the unit, and I could not trace this field through the current site client to the formatter. The reviewed endpoint payload values are in the hundreds or thousands. The site's generic latency formatter treats values as milliseconds and divides by 1,000 for seconds, so the importer estimates seconds from that scale; rows use `source_unit: "source_reported"` and `normalization_basis: "inferred_ms_scale"`. The UI labels these seconds as estimated and shows the source number. The endpoint API example uses fractional values such as 0.25, which conflicts with current payload scale and leaves a residual ambiguity.

Latency semantics are model-dependent in OpenRouter's own descriptions: model pages describe latency as total round-trip time, and OpenRouter's reasoning-metrics announcement says reasoning-model latency measures time until the first reasoning token. We therefore label the metric “Latency” and disclose this distinction instead of claiming one universal event. Throughput is tokens per second; OpenRouter says reasoning-model throughput includes reasoning and output tokens. Workload `request_count` is retained when present, but aggregate percentiles have no sample count in the endpoint response.

The OpenRouter endpoint API and UI references are [the endpoint API response example](https://openrouter.ai/docs/api/api-reference/endpoints/list-all-endpoints-for-a-model), [the client latency formatter](https://openrouter.ai/_next/static/immutable/chunks/0ocfxcm1jyw9_.js), [provider-selection latency thresholds](https://openrouter.ai/docs/guides/routing/provider-selection), [the model performance page](https://openrouter.ai/openai/gpt-chat-latest/apps), and [the reasoning metrics announcement](https://openrouter.ai/blog/announcements/better-insights-faster-metrics-and-new-developer-power-tools/). The fetched official formatter chunk had SHA-256 `3e43cf02c1c09eb606da2b82763dd9ea8e61c5ab71d2b922034a86f049e88b98`; module `219037`'s `latency` and `latency-seconds` presets render values below `999.5` with an `ms` suffix and render larger values as `value / 1000` seconds. This proves how the generic formatter works, but not that `latency_last_30m` feeds it. The endpoint response schema itself does not document latency units.

The official [OpenRouter Terraform model schema](https://github.com/OpenRouterTeam/terraform-provider-openrouter/blob/main/docs/data-sources/model.md) specifies endpoint pricing units. `prompt`, `completion`, cache-read/write, 1-hour cache-write, and internal-reasoning prices are USD per token. Token prices, including `input_cache_write_1h`, are multiplied by 1,000,000 for the stored USD-per-million-token values. Image, image-output, request, web-search, audio, audio-output, cached-audio-input, and image-token charges retain the schema's exact USD billing unit. `discount` is a fraction from 0 to 1 and is applied to all listed charges as `listed price × (1 − discount)`; the effective prices are stored and the discount fraction remains visible. Conditional `overrides` are not folded into the default quote because their conditions can depend on prompt length or time.

The UI shows the captured time and snapshot age, describes the 30-minute sampling window, and marks values stale once the capture is older than that window. It does not treat the stored snapshot as live data.

To import an endpoint snapshot, run:

```sh
python scripts/import-route-metrics.py --dataset data/curated/dataset.json --staging data/staging/openrouter-endpoints.json
```

The operation is idempotent for the same staging snapshot: current metric rows replace the previous OpenRouter endpoint rows for exactly matched routes, and price records are upserted by their existing route-scoped IDs. The importer updates matching source retrieval timestamps and hashes from the staged snapshot. Review the resulting source and dataset diff before publication.

The reviewed public response snapshot for this import is `data/expansion/openrouter-endpoints-2026-10-18.json`; pass it with `--staging` to reproduce the import offline. Unmatched endpoints are counted and require identity review before publication.
